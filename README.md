# PredictAI — Predictive Maintenance & Machine Health Platform

Machine failure prediction on industrial sensor data, built ML-first: the models are
researched, evaluated and selected in notebooks before any application code exists.

**Status:** ML research phase — notebooks 01–04 complete.

## Headline result

| Model | PR-AUC | Recall | Precision | False alarms | Expected cost |
|---|---|---|---|---|---|
| Always predict "no failure" | — | 0.000 | — | 0 | 34,000 |
| Logistic Regression (raw sensors) | 0.415 | 0.103 | 0.636 | 4 | 30,540 |
| Logistic Regression (+ engineered) | 0.458 | 0.926 | 0.109 | 517 | 7,670 |
| **XGBoost (tuned)** | **0.898** | **0.926** | **0.342** | **121** | **3,710** |

Test split, 2,000 rows, 68 failures. Thresholds selected on validation by expected-cost
minimisation, then frozen. At matched recall, the tuned model cuts false alarms by 77%.

## The finding that shaped the project

AI4I 2020 is synthetic, and its failure modes are generated by documented threshold
rules. Notebook 02 reconstructs those rules from the sensors and scores them against
their own labels:

| Failure mode | Rule recovered from sensors | Precision | Recall |
|---|---|---|---|
| Heat dissipation (HDF) | `temp_diff < 8.6 K` and `rpm < 1380` | 1.000 | 1.000 |
| Power (PWF) | `power < 3500 W` or `power > 9000 W` | 1.000 | 1.000 |
| Overstrain (OSF) | `wear × torque > tier threshold` | 1.000 | 1.000 |
| Tool wear (TWF) | `200 ≤ wear ≤ 240 min` | 0.054 | 0.935 |

Three of four modes are perfectly deterministic. TWF is not — the generator fails the
tool at a random point inside the wear window, so only 46 of the 790 rows in that window
actually fail. Combined with nine failures that carry no mode label at all, this gives an
**analytic performance envelope**:

```
84.7%  recall achievable at ~100% precision  (deterministic modes)
97.3%  absolute maximum recall               (+43 stochastic TWF failures,
                                              at ~17 false alarms each)
 2.7%  unreachable at any cost                (9 mode-less failures)
```

Every model is reported against this envelope, so the comparison answers *how close to
optimal* rather than *which number is bigger*. The tuned model's precision-recall curve
holds high precision right up to 84.7% recall and then falls off a cliff — the elbow
predicted analytically before any model was trained.

## Scope change: this dataset is not time series

The original plan called for an LSTM over sensor sequences and remaining-useful-life
regression. **AI4I 2020 has no machine identifier and no timestamp** — each row is an
independent snapshot, so there are no per-machine trajectories to learn from and no
time-to-failure to measure.

Sorting rows by tool wear and sliding a window over unrelated machines would produce a
model that looks like it works and means nothing. The sequential half of the project
therefore moves to **NASA C-MAPSS**, which has `unit_number`, `time_in_cycles` and
run-to-failure trajectories. The two datasets answer two different questions in the same
dashboard: *is this machine failing now* (AI4I) and *how long until it fails* (C-MAPSS).

## Selected findings

- **Class weighting hurt.** `class_weight='balanced'` raised recall but dropped PR-AUC
  from 0.495 to 0.409; `scale_pos_weight` on XGBoost was likewise slightly worse than
  leaving it off. Reweighting shifts the operating point without improving the ranking.
  Threshold selection achieves the same result without degrading the model.
- **The three levers, ranked by effect:** model family (largest), feature engineering
  (~4 PR-AUC points), hyperparameter tuning (a few points). Tuning is the smallest lever
  and usually receives the most attention.
- **The learning curve is still rising at full training size.** The model is
  data-limited, not capacity-limited — more failure examples would beat more tuning.
- **Permutation importance caught a duplicate feature column** that gain-based
  importance did not surface, which is why SHAP is used for the final attribution.
- **The model is confident about physics-driven failures and barely above zero on
  stochastic ones** (mean probability 0.75 vs 0.07). Tool-wear warnings therefore need a
  different UX treatment from the other alerts — a product decision falling directly out
  of the error analysis.

## Repository layout

```
predictai/
├── notebooks/          numbered research notebooks, outputs committed
├── ml/
│   ├── paths.py            canonical paths
│   ├── data.py             schema, feature engineering, frozen split
│   ├── viz.py              shared plot style
│   ├── preprocessing/      feature matrix shared by training and inference
│   ├── training/           (empty — model training lives in notebooks for now)
│   ├── evaluation/         metrics, cost model, experiment leaderboard
│   └── inference/          (empty — production inference pipeline, not yet built)
├── scripts/
│   └── download_data.py    fetch + verify the dataset
├── data/
│   ├── raw/                ai4i2020.csv
│   └── processed/          cleaned parquet + frozen split indices
├── models/
│   └── failure_classifier/ model.json, feature_config.json, model_metadata.json
├── reports/
│   ├── figures/            all generated figures
│   └── metrics/            one JSON per recorded experiment
├── backend/             FastAPI inference service — scaffolded, not implemented
├── frontend/            Next.js dashboard — scaffolded, not implemented
├── tests/               test suite — scaffolded, not implemented
├── docker/              containerisation — scaffolded, not implemented
└── docs/                architecture notes, model cards — scaffolded, not implemented
```

`backend/`, `frontend/`, `tests/`, `docker/`, `docs/` are directory skeletons only —
each holds a README describing what will land there. They stay empty on purpose until
notebooks 05–10 select a final model; building the application around a model that
doesn't exist yet is the mistake this project is structured to avoid.

Notebooks import from `ml/` rather than redefining logic. The split, the feature
definitions, the cost model and the evaluation function each exist in exactly one place,
so no two notebooks can silently disagree about what they are measuring.

## Reproducing

```bash
pip install -r requirements.txt
python scripts/download_data.py
jupyter lab notebooks/
```

Run the notebooks in order — 01 writes the cleaned data and the frozen split that the
rest depend on. Seed is 42 throughout.
